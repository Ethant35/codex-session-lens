# Architecture
Author: Ethan

Codex Session Lens is a companion HUD, not a native Codex extension. Electron was selected for supported real-app Playwright automation and native window controls; its bundled Node SQLite avoids a separately compiled database addon. Electron hosts a React renderer. TypeScript runs in both processes. A sandboxed preload exposes six narrow asynchronous operations. The renderer has no Node access, remote content, filesystem API, or general IPC interface. The main process checks the sender and validates preference inputs. Chromium requests outside the bundled renderer are blocked; the CSP disallows connections. There is no server, account integration, updater, analytics SDK, or credential reader.

## Data path
Configured directories → recursive read-only JSONL discovery → incremental UTF-8 framing → allowlisted telemetry projection → SQLite → validated IPC → React.

The default sources are `$CODEX_HOME/sessions` and `$CODEX_HOME/archived_sessions`, with `~/.codex` as the default home. Only uncompressed `.jsonl` files are supported. The app ignores symlinks and limits directory nesting. It checks for appends every second; incomplete trailing lines wait for the next append. Oversized lines are discarded with a diagnostic. Inode changes, size decreases, and same-size modification trigger replay. A missing source does not delete local history. Paths can be changed in Settings.

Session identity comes only from `session_meta.payload.id`, not filenames, working directories, model names, or activity times. A record with a conflicting thread identity is skipped. SHA-256 event fingerprints make replay idempotent. Only allowlisted telemetry observations, session projections and fingerprints are stored, never raw payloads or prompts. Each scan commits new observations, fingerprints and rebuilt projections in one SQLite transaction; secure deletion runs when clearing data; freed database pages remain allocated for reuse. Files use owner-only permissions. Clear also pauses ingestion, so the next scan does not immediately repopulate history. Original Codex files are never changed.

## Accounting contracts
- `event_msg` / `token_count` / `info.total_token_usage` is the authoritative cumulative snapshot. Replace it; never add it to an earlier cumulative value.
- `token_usage_record.thread_token_usage`, when present, is another cumulative snapshot, not another billable response to add. `usage` is its latest-request sample. Missing cumulative usage is not reconstructed from an incomplete response history.
- Cached input is a subset of input. It is shown separately but never added to input. Output already includes reasoning; reasoning is not added again.
- Missing, negative, unsafe-integer, or internally inconsistent usage is unavailable. Counter regressions retain prior totals with an explicit uncertainty warning. Late observations are retained and projected in timestamp order; status activity cannot suppress model or usage evidence. Conflicting equal-time values are unavailable until newer evidence arrives. A timestamp does not prove order within that timestamp; even same-file conflicts use this conservative rule.
- Latest-request usage is shown separately from lifetime totals. A context estimate is produced only when that same token-count record contains a complete latest total and a positive context limit. The ratio is latest total / limit. It is **not exact current occupancy**, does not subtract Codex UI's baseline allowance, and is not promised to match Codex's remaining-context display. Turn-context records, new tasks, compaction, and samples without a complete limit invalidate the estimate. A boundary at the same timestamp wins over the sample because cross-file order is unknown.
- `compacted` and `context_compacted` record known compactions, deduplicated when their timestamps match. Different timestamps remain separate observations; missing events cannot establish that no compaction occurred.
- `session_meta.source.subagent.thread_spawn.parent_thread_id` provides an observed parent relationship. Child totals never merge into parent totals. Missing identity is unavailable. Status is the last recorded task status, not a liveness guarantee.

## Desktop selection investigation
On 2026-10-22 the installed CLI was 0.163.0; desktop was com.openai.codex in ChatGPT.app, version 26.1016.61520, emitting 0.163.0-alpha.11.1 rollout metadata. The documented [Codex app-server](https://learn.chatgpt.com/docs/app-server) protocol can start and manage client-owned threads and deliver usage notifications. No documented foreground desktop conversation API was established in this investigation. Starting a second app-server does not establish which conversation is selected in another application.

A read-only macOS Accessibility probe confirmed the desktop was running but reported that assistive access was not granted. No permissions were changed. No reliable automatic selection was verified. v1 therefore implements a persistent manual selector with search by session ID/model, activity sorting and recent selections. A newly active session never overrides the manual selection. Accessibility-based automatic switching is not implemented. Activity order is not foreground detection.

Parser structure was checked against the installed rollout schema and the upstream [Codex protocol](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/protocol.rs), including TokenUsageInfo, TokenUsageRecord and SubAgentSource. These formats can change; unsupported records are ignored. See ACCEPTANCE.md for the exact locally tested version and evidence.

## Replay and upgrade (v1.0.1)
Each scan writes bounded batches of128 sanitized observations inside one transaction, then streams changed sessions through a timestamp/key index. The projection yields every256 rows. Service writes share one queue so settings and window changes cannot enter an open scan transaction. Cancellation rolls back observations, fingerprints and session projections together. Repeated cumulative records replace rather than add. The persistent observation set makes the result independent of discovery order and restart boundaries. Observations use the existing SHA-256 raw-record fingerprint; semantically identical records with different serialization remain harmless repeated snapshots. Equal-time distinct values produce an explicit warning instead of selecting whichever file was read last. Compaction history is chronological.

The v1 database upgrade is transactional. It seeds known values and provenance into the observation table, retains preferences and history, and clears old seen hashes once so previously suppressed source records can replay. Real source evidence replaces a seed at the same metric timestamp. An upgrade warning discloses incomplete historical coverage. When v1 had an unavailable context after a known sample, a conservative boundary at the last cached activity prevents reviving that estimate without newer evidence. Missing source history cannot be reconstructed. Clear deletes observations as well as projections and hashes.

Projection work scales with the retained telemetry observations for changed sessions. There is no raw-message archive, periodic upload, or additional UI feature. The patch tests file-order permutations, delayed discovery, overlap, restarts, equal-time conflicts and actual v1 database migration through the packaged application.

Pinned schema: [Codex rust-v0.163.0, commit 83086188ae0614bd882818ff1aa23f3194962012](https://github.com/openai/codex/blob/83086188ae0614bd882818ff1aa23f3194962012/codex-rs/protocol/src/protocol.rs). TokenUsageInfo distinguishes cumulative from latest usage; TokenUsageRecord contains response usage and cumulative thread usage. The upstream fill_to_context_window path can produce a total-only estimate, so a complete input-plus-output sample remains mandatory for our context ratio. Source timestamps and payloads are observations, not guaranteed perfect wall-clock or billing truth.

## Setup, recovery and diagnostics
LensService validates copied requests and publishes preferences only after storage succeeds. Fresh installs do not scan before setup is completed or skipped. Legacy preferences default to completed setup. Synthetic sample data exists only in snapshots; it preserves the real selection and never enters SQLite telemetry tables.

CacheHost converts startup cache errors to an inline recovery state. Retry does not replace the cache. Known invalid/corrupt data can be moved into a private sibling backup directory only after an explicit rebuild action and a new open attempt. Lock/permission/unavailable errors remain retry-only. Shutdown cancels queued recovery and stops ingestion before final bounds are saved and SQLite closes. Fatal exceptions exit with a fixed message instead of a modal dialog or raw stack.

Local diagnostics retain at most100 allowlisted events (under64KiB), including an opaque run identifier, entry point, version, timestamp and fixed error category. No exception message, source text, session ID or directory is recorded. This is local support history, not analytics. See docs/operations.md and docs/core-readiness.md for limitations and measured workloads.
